1. What Sprint 1 delivers

Sprint 1 turns the frontend prototype of Milestone 2 into a real backend for the first part of the platform. The backend is a small Flask application with a SQLite database. It covers eight user stories from Milestone 1: registration and login, the student and mentor profiles, the admin dashboard, role-based access and match creation. Confirming matches, email notifications, status changes, feedback, Smart Match and Mentorship Pulse are planned for Sprint 2.

2.4 Error handling

Every error answers with the same body {"error": "message"}. 400: missing or invalid input (the message names the field). 401: not logged in, or a wrong or expired token. 403: logged in but the role may not do this. 404: the record does not exist. 409: valid request that conflicts with the current state, for example a duplicate email, a mentor who is not verified, a mentor with no free place, or a student who already has a match. Wrong types in the JSON (for example a number where text is expected) also answer 400.

3. Design of the backend

The code is kept small and split by job, so each part is easy to read and to debug.

PartJob
routes/ (auth, profiles, admin, matches)Thin functions: read the JSON, call a function, return the answer.
validators.pyInput checks. Each function returns an error message or nothing.
services/ (matching, profiles, notifications)The real work: matching rules and score, saving profiles, writing notifications.
models.pyThe database tables, the same as the ER diagram of Milestone 2.
auth_utils.pyPassword hashing, login tokens, and the login_required and role_required checks that protect every route.

Role-based access (US-C06). The check is made on the server for every route: students and mentors only reach their own profile, and only the admin reaches the dashboard, both profile types and match creation. Hiding a link in the frontend is never the only protection.

Matching rules (US-C02). A mentor can be proposed only if verified, with a free place (proposed and active matches count), and the student has no proposed or active match. The score is out of 100: topics 70 (the share of the student's wanted topics the mentor covers) plus experience 30 (years, up to 10). These are the same rules as the frontend prototype.

6. Bugs found by testing

While designing test cases with wrong input types we found that the first version of the backend crashed with an internal error (HTTP 500, and a broken database session for the next request) instead of answering 400. We fixed these and kept the tests so they cannot come back.

Input sentActual output before the fixOutput after the fixFix
PUT /api/students/me with needs_text as a numberServer error: object of type int has no len()400 needs_text must be text.Every text field is checked to be text (validators.py)
PUT /api/students/me with skills as a listDatabase error (unsupported type); the next request also failed with a broken session400 skills must be text.Same check; the 500 handler now rolls the session back
POST /api/auth/register or login with a JSON list instead of an objectServer error: list has no attribute get400 (register) and 401 (login) with a clear messageOne helper, json_body(), treats anything but an object as empty
PUT /api/mentors/me with bio as a list or qualifications as a numberServer error / database error400 bio must be text.Same text check for mentor fields

8. How to run the backend

The backend is in the folder backend. The README explains the steps: create a virtual environment, pip install -r requirements.txt, then python app.py (the server listens on port 5001). The first start creates the database, the eight topics and one admin account (admin@client.test, password demo123). Run the tests with pytest -v.
